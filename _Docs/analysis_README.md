# Анализ данных, сформированных GigaChat

Источник данных: GigaChat. Сценарий загрузки использует PostgreSQL (RETURNING, ON CONFLICT, изменяющие данные CTE); он не заявлен как ANSI-92.
Основа: база после второй миграции. Скрипт загрузки выполнять один раз. Идентификаторы после удаления прежних тестов не сбрасывались.

## Исходный промпт
Напиши SQL-скрипт для PostgreSQL, который добавит тестовые данные метеорологических измерений в существующую базу.

Структура таблиц:
- users: id — автоматически генерируется, full_name — ФИО, position_id — ссылка на должность.
- batches: id — автоматически генерируется, user_id — ссылка на сотрудника, equipment_type_id — ссылка на оборудование.
- parameters: id — автоматически генерируется, batch_id — ссылка на пачку, parameter_type_id — ссылка на тип параметра, value — DECIMAL(10,2), measurement_date — DATE. Тип параметра и дата обязательны.
- parameter_types: id — целочисленный первичный ключ без автогенерации, name — название, measurement_unit_id — ссылка на единицу.
- measurement_units: id — целочисленный первичный ключ без автогенерации, name — название, symbol — обозначение.

Уже существуют:
- Должности: 1 — старший метеоролог, 2 — оператор-вычислитель.
- Оборудование: 1 — десантный метеокомплект, 2 — ветровое ружьё.
- Единицы: 1 — метр (м), 2 — метр в секунду (м/с), 3 — градус Цельсия (°C).
- Типы параметров: 1 — высота метеопоста, единица 1; 2 — температура, единица 3; 3 — скорость ветра, единица 2; 4 — дальность сноса пуль, единица 1.

Добавь пятый тип параметра — относительную влажность в процентах — и нужную единицу измерения, если их ещё нет.
Добавь несколько сотрудников, пачки и измерения для них. Пусть данные будут разнообразными, чтобы на них можно было выполнить учебный анализ качества данных.
Существующие записи не удаляй. Учти, что в базе уже могут быть данные и занятые идентификаторы. Не меняй структуру таблиц. Верни полный SQL-скрипт.

## Уточнение 1
В твоём скрипте ошибка со ссылками: сотрудники и пачки получают автоматические id, поэтому нельзя предполагать, что новые записи получат номера 1, 2, 3, 4. Эти номера могут быть заняты, а после удаления записей счётчики не сбрасываются.
Перепиши скрипт так, чтобы получать реальные id добавленных сотрудников и пачек и использовать их для связей. Можно использовать PostgreSQL RETURNING.
Сохрани предложенные значения измерений, включая аномалии и NULL. Существующие данные не удаляй. Оберни выполнение в транзакцию. Верни полный исправленный скрипт.

## Уточнение 2
В скрипте остались две ошибки выполнения:
1. inserted_batches возвращает RETURNING id, user_id, но основной запрос использует b.equipment_type_id. Добавь equipment_type_id в RETURNING.
2. В VALUES внутри CROSS JOIN LATERAL даты записаны строками. Используй типизированные литералы DATE '2024-05-01' для всех дат, чтобы measurement_date имел тип DATE.
Исправь только эти ошибки выполнения. Остальную логику и данные сохрани для дальнейшего анализа. Верни полный скрипт.

Границы учебные, не нормативные: высота -500..9000 м; температура -90..60 °C; ветер 0..100 м/с; дальность сноса 0..1000 м; влажность 0..100%.

Пачки 1 и 2 относятся к исходным данным первой миграции, а не к генерации GigaChat. По критерию пяти параметров они неполные.
GigaChat создал Сидорову два набора измерений в одной пачке. Обещанная в комментариях вторая пачка Иванова не создается: данные за 4–5 мая, включая -99.99 °C, не вставляются. Поэтому запрос диапазонов их не показывает.
Проверка единиц выполняется на уровне справочника: схема назначает единицу типу параметра, а не отдельному измерению.
